# Sixteen Ledger Update Cards

Optional print handouts for the chapter-by-chapter route. These are fictional teaching aids, not evidence of a validated design.

## Extended print kit: sixteen Ledger update cards

Use one card after its chapter. These are intentionally short, so a team can
keep the same promise in view without pretending each chapter begins a new
case. The cards are proposed learning aids, not canonical records or evidence.

<div class="pagebreak"></div>

### Card 1: promise before steps

Write the beneficiary, promise, and acceptable endings. Cross out any step
that is being mistaken for an outcome.

| Promise | Beneficiary | Business owner | Terminal evidence | Unknown |
| --- | --- | --- | --- | --- |
| | | | | |

**Ask:** If no worker runs again, who is still responsible for this promise?

<div class="pagebreak"></div>

### Card 2: three clocks

Separate request wait, processing window, and business commitment. A short
client deadline is not permission to abandon the beneficiary.

| Request clock | Processing clock | Business clock | Owner after request returns | Escalation |
| --- | --- | --- | --- | --- |
| | | | | |

**Ask:** Which clock changes what the organization owes?

<div class="pagebreak"></div>

### Card 3: distributed participants, one open promise

List facts participants may declare, then name the authoritative case state and
its owner. A participant's silence must have a governed consequence.

| Participant fact | Authoritative case state | Next action | Escalation owner | Closure evidence |
| --- | --- | --- | --- | --- |
| | | | | |

**Ask:** Which component would still know the promise is open if every other
component reported only its local status?

<div class="pagebreak"></div>

### Card 4: progress and authority

Replace a generic status with the meaning, progress evidence, transition, and
actor. Activity is not progress when it cannot change the beneficiary outcome.

| State | Meaning | Progress evidence | Permitted transition | Authorized actor |
| --- | --- | --- | --- | --- |
| | | | | |

**Ask:** Who may move this case, and which evidence makes that move legitimate?

<div class="pagebreak"></div>

### Card 5: checkpoint versus effect

Record what durable history preserves and what it cannot establish outside its
boundary. Attach a participant-owned effect identity before replay is allowed.

| Checkpoint | External effect | Effect identity | Independent evidence | Gap owner |
| --- | --- | --- | --- | --- |
| | | | | |

**Ask:** If replay repeats this action, what could happen twice?

<div class="pagebreak"></div>

### Card 6: retry under uncertainty

Write the prior-effect knowledge state before selecting an attempt count.
Unknown means query, reconcile, or stop—not a library-default repeat.

| Operation ID | Attempt ID | Known/unknown effect | Query-before-repeat | Budget | Exhaustion owner |
| --- | --- | --- | --- | --- | --- |
| | | | | | |

**Ask:** Which fact—not exception text—permits another attempt?

<div class="pagebreak"></div>

### Card 7: correction and residue

Keep the original effect visible. A correction is separately authorized forward
work, and an inverse balance entry may leave a human or contractual residue.

| Original effect | Correction eligibility | Correction ID | Residue | Accepting owner |
| --- | --- | --- | --- | --- |
| | | | | |

**Ask:** What cannot be undone even if the correction succeeds?

<div class="pagebreak"></div>

### Card 8: human decision is work

Give a person a decision, evidence, authority scope, deadline, substitute, and
escalation. A shared queue supplies none of these by itself.

| Decision | Assignee | Authority limit | Expiry | Substitute | Escalation |
| --- | --- | --- | --- | --- | --- |
| | | | | | |

**Ask:** What happens if the human never arrives?

<div class="pagebreak"></div>

### Card 9: waking work

When a timer fires, record whether it creates a reminder, new occurrence, or
authorized transition for the existing promise.

| Business time | Wake-up meaning | Late-evidence rule | Decision authority | Consequence owner |
| --- | --- | --- | --- | --- |
| | | | | |

**Ask:** What does being late change besides a status label?

<div class="pagebreak"></div>

### Card 10: convergence is a decision

List unequal branch meanings and the person who can choose what to accept,
wait for, compensate, cancel, or escalate.

| Branch result | Authority | Cancellation rule | Convergence decision | Residual owner |
| --- | --- | --- | --- | --- |
| | | | | |

**Ask:** Which two green branches could still produce an unacceptable outcome?

<div class="pagebreak"></div>

### Card 11: child returns responsibility

Define the child sub-promise and its return contract. The parent retains the
beneficiary promise even while a child is independently running.

| Child promise | Parent owner | Progress receipt | Cancellation/compensation | Orphan response |
| --- | --- | --- | --- | --- |
| | | | | |

**Ask:** If the child disappears, who notices and what remains owed?

<div class="pagebreak"></div>

### Card 12: one acceptable outcome

Count delivery, attempt, workflow state, effect, notice, and outcome
separately. Do not let one layer's success stand for another's.

| Layer | Identity | Evidence | Known gap | Reconciliation owner |
| --- | --- | --- | --- | --- |
| | | | | |

**Ask:** What makes `completion_unproven` more truthful than `complete`?

<div class="pagebreak"></div>

### Card 13: open work through change

Record the definition and policy governing this instance, then choose a cohort
treatment rather than letting deployment rewrite its historical meaning.

| Old version | New version | Cohort | Approved treatment | Owner | Evidence |
| --- | --- | --- | --- | --- | --- |
| | | | | | |

**Ask:** Which promise is still open under the old meaning?

<div class="pagebreak"></div>

### Card 14: quarantine before repair

Freeze contradictory evidence, classify the problem, and separate diagnosis,
approval, execution, verification, and closure authority.

| Classification | Frozen evidence | Repair ID | Approver | Executor | Verifier | Residual owner |
| --- | --- | --- | --- | --- | --- | --- |
| | | | | | | |

**Ask:** What could a repair repeat, conceal, or prematurely close?

<div class="pagebreak"></div>

### Card 15: test the consequence

Attach each test to the promise, clock, effect, authority, expected safe stop,
and evidence limit. A passing result must state what it cannot prove.

| Adverse move | Expected response | Evidence retained | Nonclaim | Owner after inconclusive result |
| --- | --- | --- | --- | --- |
| | | | | |

**Ask:** Which failure result should block a release or change the design?

<div class="pagebreak"></div>

### Card 16: governed agent contribution

Treat a fluent recommendation as a candidate. Record the sources, withheld
tools, approval boundary, stop condition, and human owner of uncertainty.

| Agent role | Permitted sources | Withheld transition | Stop reason | Escalation owner | Trace gap |
| --- | --- | --- | --- | --- | --- |
| | | | | | |

**Ask:** What can the agent not infer or do when effect evidence is missing?

<div class="pagebreak"></div>

### Capstone card: refuse completion

Use this once the case reaches `completion_unproven`. The correct result may be
an owned unknown, a new authorized promise, or an appeal—not a terminal label.

| Missing evidence | Prohibited action | Next permitted action | Owner | Next review | Closure rule |
| --- | --- | --- | --- | --- | --- |
| | | | | | |

**Ask:** What would make a partner believe this case is over when it is not?

<div class="pagebreak"></div>

### Handoff card: who owns the unfinished consequence?

Give this to the receiving role at the end of the lab. The handoff is not
complete until a person or accountable role accepts the named consequence.

| Field | Entry |
| --- | --- |
| Unfinished consequence | |
| Receiving owner and authority accepted | |
| Evidence gap and prohibited action | |
| Due point and escalation | |
| Reconsideration trigger and closure rule | |

**Ask:** Can the recipient explain the next safe move without assuming missing
facts, using a stale approval, or repeating an effect?
